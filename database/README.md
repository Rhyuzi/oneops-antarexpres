# OneOps Database — phpMyAdmin Deployment Guide

This directory contains the SQL migrations and seed data for the **Data Warrior**
document management module (OneOps / AntarXpress).

All files are plain SQL, designed to be imported manually through **cPanel →
phpMyAdmin**. No SSH or CLI database access is required.

---

## 1. Files and import order

Import in this exact order (foreign keys depend on earlier tables):

| Order | File | Creates |
|---|---|---|
| 1 | `migrations/001_create_users_roles.sql` | `users`, `roles`, `user_roles` + default roles |
| 2 | `migrations/002_create_storage_folders.sql` | `storage_folders` |
| 3 | `migrations/003_create_storage_files.sql` | `storage_files` |
| 4 | `migrations/004_create_storage_file_versions.sql` | `storage_file_versions` |
| 5 | `migrations/005_create_storage_folder_permissions.sql` | `storage_folder_permissions` |
| 6 | `migrations/006_create_storage_audit_logs.sql` | `storage_audit_logs` |
| optional, last | `seeds/001_initial_storage_folders.sql` | 7 root folders (Company Documents, Finance, HR, Operational, Management, IT & Infrastructure, Archive) |

> **If your database already has `users` / `roles` / `user_roles` tables**
> (for example from a previous OneOps deployment): **skip file 001**. The
> storage tables only require that a `users` table with an INT UNSIGNED
> auto-increment `id` and a `roles` table with the same exist. See
> *Appendix B — using pre-existing users/roles tables* below.

Every file uses `CREATE TABLE IF NOT EXISTS` and `INSERT IGNORE`, so re-importing
a file that already ran will not error and will not duplicate data.

## 2. Requirements

- MySQL 5.7+ or MariaDB 10.2+ (any cPanel default from the last several years).
- The database user must have `CREATE`, `ALTER`, `INDEX`, `INSERT` privileges
  on the target database.

## 3. Access phpMyAdmin through cPanel

1. Log in to cPanel (`https://yourdomain.com:2083` or the URL your host provides).
2. In the **Databases** section, click **phpMyAdmin**. It opens already
   logged in with your cPanel database user.
3. In the left-hand tree, click the database you use for OneOps
   (cPanel names usually look like `cpaneluser_oneops`).

## 4. Back up the database FIRST (do this before importing anything)

1. Select the OneOps database in the left tree.
2. Click the **Export** tab (top bar).
3. Choose **Quick** method, **SQL** format → click **Go**. A `.sql` file
   downloads. Keep it somewhere safe.
4. If anything goes wrong, restore via **Import** → choose the downloaded
   file → **Go**.

## 5. Import each migration

For each file in the order listed above:

1. Select the OneOps database in the left tree (the database itself,
   not any table).
2. Click the **Import** tab.
3. Click **Choose File** and select the `.sql` file.
4. Leave charset as `utf-8` and all other options at their defaults.
5. Scroll down and click **Go**.
6. Wait for the green success banner ("Import has been successfully
   finished"). Only then import the next file.

phpMyAdmin executes the whole file at once; partial imports should not
happen, but if one does, see *Troubleshooting* below.

## 6. Import the optional seed

After all six migrations, optionally import
`seeds/001_initial_storage_folders.sql` the same way. It creates the seven
root folders **only if a root folder with that name does not already exist** —
safe to run more than once.

The seed intentionally grants **no permissions** to any role. Only the
`super_admin` role (which bypasses permission checks entirely) can see the
folders initially. Assign access per role afterwards in Data Warrior:
open a folder → **Manage Permissions**.

## 7. Verify the tables

After importing, in phpMyAdmin:

1. Click the OneOps database in the left tree.
2. Confirm these tables are listed (column counts may differ by version):
   - `users` (8 columns)
   - `roles` (4 columns)
   - `user_roles` (3 columns)
   - `storage_folders` (9 columns)
   - `storage_files` (16 columns)
   - `storage_file_versions` (9 columns)
   - `storage_folder_permissions` (13 columns)
   - `storage_audit_logs` (7 columns)
3. Click `roles` → **Browse**: you should see six rows
   (super_admin, management, finance, hr, operational, it).
4. If you imported the seed, click `storage_folders` → **Browse**: seven
   root folders with `parent_id = NULL`.

## 8. Create the first Super Admin user

Migration 001 intentionally creates **no users** (password hashes must be
generated by the app, never stored in plain SQL). To create the first admin:

**Option A — seed an admin via SQL (fast):**

Run this in phpMyAdmin's **SQL** tab after replacing the values shown in
CAPS. Get the hash by running on your local machine
(`npm run hash-password 'YourPassword'` from the project root — it prints
a bcrypt hash; paste it below):

```sql
INSERT INTO users (username, email, full_name, password_hash, is_active)
VALUES ('admin', 'ADMIN_EMAIL', 'Super Admin', 'PASTE_BCRYPT_HASH_HERE', 1);

INSERT INTO user_roles (user_id, role_id)
SELECT u.id, r.id FROM users u, roles r
WHERE u.username = 'admin' AND r.name = 'super_admin';
```

**Option B — the app does it for you:**

If the `users` table is empty when the server starts, the backend
auto-creates an `admin` user with the password from the `BOOTSTRAP_ADMIN_PASSWORD`
environment variable (change it immediately after first login, and only set
that variable when you actually want this to happen).

## 9. Troubleshooting foreign key errors

**"#1215 — Cannot add foreign key constraint"** almost always means an
earlier migration was skipped or an existing table uses different column
types. Check:

1. `users.id` and `roles.id` must be `INT UNSIGNED AUTO_INCREMENT`.
2. Files were imported in the correct order (001 before 002, etc.).
3. Tables use InnoDB (phpMyAdmin → table → **Operations** → storage engine).
   MyISAM tables cannot have foreign keys. `ALTER TABLE t ENGINE=InnoDB;`
   converts one.

**"#1452 — Cannot add or update a child row"** during seed import: the seed
references a `super_admin` user only if one exists; it inserts folders with
`created_by = NULL` otherwise, so this error should not occur. If it does,
verify `user_roles` contains at least one super_admin row — or temporarily
remove the `LEFT JOIN ... u` lines and insert with NULL created_by.

**"#1005 — errno 150"**: same as 1215 — mismatched types or a missing
referenced table. Confirm both tables exist and both key columns are
`INT UNSIGNED`.

**Partial import / timeout on shared hosting**: phpMyAdmin sometimes times
out on large files; these files are small (a few KB) so this is unlikely. If
it happens, re-run the same file — `CREATE TABLE IF NOT EXISTS` makes it safe.

## 10. Rollback safely

Because every migration uses `IF NOT EXISTS` and only adds tables, rollback
is a clean drop of the storage tables (in reverse dependency order). Run in
the phpMyAdmin **SQL** tab **only if you want to remove Data Warrior**:

```sql
SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS storage_audit_logs;
DROP TABLE IF EXISTS storage_folder_permissions;
DROP TABLE IF EXISTS storage_file_versions;
DROP TABLE IF EXISTS storage_files;
DROP TABLE IF EXISTS storage_folders;
SET FOREIGN_KEY_CHECKS = 1;
```

> Do **not** drop `users` / `roles` / `user_roles` unless you are removing
> OneOps entirely — the login system depends on them.

Before dropping anything, take a fresh **Export** backup (section 4).

## Appendix A — Schema summary

```
users ──< user_roles >── roles
  │                        │
  │                        └──< storage_folder_permissions >── storage_folders (self-ref parent_id)
  │                                                                   │
  ├──< storage_files ─────────────────────────────────────────────────┘
  │        │
  │        └──< storage_file_versions
  └──< storage_audit_logs
```

- Soft deletion (`deleted_at`) on folders and files; audit logs are append-only.
- `storage_files.object_key` is unique per (provider, bucket) — permanent R2
  object references; presigned URLs are always generated on demand, never stored.
- `storage_folder_permissions` rows are per (folder, role) with nine boolean
  capabilities; a missing row means "no explicit grant". Effective permission =
  nearest ancestor's grant (inheritance) unless a nearer row overrides.

## Appendix B — using pre-existing users/roles tables

If your database already had `users`/`roles` before Data Warrior (i.e. you
skipped migration 001), the foreign keys in 002–006 require:

- `users.id` — `INT UNSIGNED` auto-increment primary key.
- `roles.id` — same.

If your existing tables use `BIGINT` ids instead, edit each migration before
importing: change every `INT UNSIGNED` that references `users(id)`/`roles(id)`
(`created_by`, `updated_by`, `uploaded_by`, `user_id`, `role_id`) to
`BIGINT UNSIGNED` so the types match. Foreign keys require **identical**
column types on both sides.
